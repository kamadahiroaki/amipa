# 前処理は何をしているか

GFA を 5 段で多解像度アトラスに変える。各段の出力は `work/` に残るので、
途中からやり直せる。

```
GFA ─① 抽出 ─▶ 配列中間 ─② バブル分解 ─▶ バブル木
                    │
                    └─③ 階層化 ─▶ 解像度の階層 ─④ レイアウト ─▶ 座標 ─⑤ アトラス化 ─▶ SQLite
```

### ① 抽出（distill）

GFA を 1 回だけ走査し、ノード・エッジ・パス・塩基配列を密な整数 ID の配列に落とす。
以降の段は GFA を読まない。全ゲノム規模ではここが唯一の全文走査になる。

### ② バブル分解（decompose）

グラフの入れ子になったバブル（分岐して再合流する部分構造）を検出し、木として書き出す。
外部ツール [povu](https://github.com/pangenome/povu) を使う。

> povu の出力や用語には flubble という語が出てくる。これは povu が定義するバブルの呼び名で、
> AMIPA 側では一貫して「バブル」と呼ぶ（同じものを指す）。

### ③ 階層化（lod）

バブル木とグラフのコミュニティ構造（Infomap）を 1 本の木にまとめ、どのノードをどの解像度で
見せるかを決める。バブルの入れ子だけでは粒度が飛び飛びになり、コミュニティだけでは生物学的な
構造と対応しないので、両方を合わせている。粗い層ほど 1 つのノードが多くの実ノードを代表する。
この段は再現性のため 1 スレッド固定（並列化すると結果が変わる）。

### ④ レイアウト

トポロジだけから 2 次元座標を決める（PivotMDS で初期化した確率的勾配降下）。
ゲノムの一次元性に引きずられず、バブルの入れ子構造が見える配置になる。

### ⑤ アトラス化（emit）

層ごとにノードとエッジを SQLite へ書き、検索索引・参照座標・塩基配列・ハプロタイプ被覆を載せる。
空間索引は本体には持たず、次のタイル索引の段が別ファイルに作る。

この段はランダム書き込みが支配的なので、`--tmp` にローカルの速いディスクを指定すると
大幅に速くなる（共有ファイルシステム上で直接組むとネットワーク待ちになる）。

## 付随する段

| 段 | 何をするか |
|---|---|
| アノテーション | 生の注釈ファイル（染色体バンドの表・GTF・BED）を読み、参照座標やパスをたどって各ノードに射影する。外部ツールは使わない。本体は書き換えずサイドカーに書く |
| リード | GAF を seekable zstd（256KiB ごとの独立フレーム＋シークテーブル）に詰め替え、索引だけをサイドカーに置く。実体は該当フレームだけ展開して 1 行を取り出す。表示に使わないタグ（既定 `bq:Z`）は保存しないので、同じ内容が BGZF の 1/8 に収まる |
| タイル索引 | ノードとエッジを層ごとにタイル順（Z-order）へ並べ直したサイドカー。表示範囲の取得・件数の見積り・ハプロタイプ絞り込み・線の太さ（ハプロタイプ幅・リード支持）をすべてここから引く。矩形の問い合わせが連続した範囲の読み出しになるので、ネットワークファイルシステム上の大きなアトラスでも表示範囲の取得が数秒から数十ミリ秒になる。既定で作り、リードを足したときは作り直す |

いずれもアトラスを作り直さずに後から足せる。
