# 前処理は何をしているか

GFA を 5 段で多解像度 DB に変える。各段の出力は `work/` に残るので、
途中からやり直せる。

```
GFA ─① 抽出 ─▶ 配列中間 ─② バブル分解 ─▶ バブル木
                    │
                    └─③ 階層化 ─▶ 解像度の階層 ─④ レイアウト ─▶ 座標 ─⑤ DB 化 ─▶ SQLite
```

### ① 抽出（distill）

GFA を 1 回だけ走査し、ノード・エッジ・パス・塩基配列を密な整数 ID の配列に落とす。
以降の段は GFA を読まない。全ゲノム規模ではここが唯一の全文走査になる。
圧縮（`.gz`・`.zst`）のまま読む。重なりのある L 行（CIGAR が `0M` でない）があればここで止まる。
GFA ヘッダの `RS:Z`（参照の sample）を記録し、参照の選び方（[usage-prep.md](usage-prep.md#参照--ref-key)）に使う。

### ② バブル分解（decompose）

グラフの入れ子になったバブル（分岐して再合流する部分構造）を検出し、木として書き出す。
外部ツールを 1 つ選んで使う（`--decomposer`）。

| 分解器 | 特徴 |
|---|---|
| `bubblefinder`（既定） | [BubbleFinder](https://github.com/algbio/BubbleFinder) の ultrabubble。最も速く軽い（全ゲノム規模で数分・数十 GB）。ただし内部に閉路を含むバブル（縦列反復や環状ゲノムの一部）は定義上出さないので、その部分は次の段で細切れの階層になる |
| `billi` | [Billi](https://github.com/at-cg/billi) の panbubble。閉路を含むバブルも見つけ、入れ子の親子関係もより正しく出す。BubbleFinder より数倍遅く重い。1 スレッド |

どちらの分解器でも出力は同じ形式（`.pvst`）に揃え、次の段はそれだけを読む。分解の前に入力から
パス（P 行・W 行）を除く。Billi と BubbleFinder は端の無い連結成分（純粋な環）があると止まるので、
そのときだけ成分ごとに分岐の無い 1 点で環を開いてやり直し、結果をもとのノードに戻す。

配布しているコンテナイメージには Billi が入っていない（Billi のリポジトリにはライセンスの表示が無く、
再配布できないため）。Billi を使うときは自分で入手してビルドし、
`--billi` で場所を渡す（環境変数 `AMIPA_BILLI` でもよい）。

> 分解器ごとにバブルの呼び名が違う（BubbleFinder は ultrabubble、Billi は panbubble）。
> AMIPA 側では一貫して「バブル」と呼ぶ。

### ③ 階層化（lod）

バブル木とグラフのコミュニティ構造（Infomap）を 1 本の木にまとめ、どのノードをどの解像度で
見せるかを決める。各ノードは、それを内部に含む最も深いバブルに属させる（深いバブルから順に、入口から
出口までの内部を辿って割り当てる。外側のバブルを辿るときは内側のバブルに割り当て済みの部分も通り抜ける）。バブルの入れ子だけでは粒度が飛び飛びになり、コミュニティだけでは生物学的な
構造と対応しないので、両方を合わせている。粗い層ほど 1 つのノードが多くの実ノードを代表する。
この段は再現性のため 1 スレッド固定（並列化すると結果が変わる）。

### ④ レイアウト

トポロジだけから 2 次元座標を決める（PivotMDS で初期化した確率的勾配降下）。
ゲノムの一次元性に引きずられず、バブルの入れ子構造が見える配置になる。

### ⑤ DB 化（emit）

層ごとにノードとエッジを SQLite へ書き、検索索引・参照座標・塩基配列・ハプロタイプ被覆を載せる。
空間索引は本体には持たず、次のタイル索引の段が別ファイルに作る。

この段はランダム書き込みが支配的なので、`--tmp` にローカルの速いディスクを指定すると
大幅に速くなる（共有ファイルシステム上で直接組むとネットワーク待ちになる）。

## 付随する段

| 段 | 何をするか |
|---|---|
| アノテーション | 生の注釈ファイル（染色体バンドの表・GTF/GFF3・BED）を読み、参照のパスをたどって各ノードに射影する（パスの無いグラフでは作らない）。外部ツールは使わない。本体は書き換えずサイドカーに書く |
| リード | GAF を seekable zstd（256KiB ごとの独立フレーム＋シークテーブル）に詰め替え、索引だけをサイドカーに置く。実体は該当フレームだけ展開して 1 行を取り出す。表示に使わないタグ（既定 `bq:Z`）は保存しないので、同じ内容が BGZF の 1/8 に収まる |
| 通過（trav） | 錨（ハプロタイプの中で 1 回だけ通り、多くのハプロタイプが同じ順で通るノード）を選んで合意座標に並べ、各コンティグのウォークを座標の単調な区間（通過）に切る。同じ区間を 2 回通るコンティグは通過 2 つ（重複）。参照パスの順を手掛かりに向きと染色体の順を決める。パスがあれば既定で作る |
| 遺伝子（genes） | 株ごとの GFF（GFF3・GTF）を流し読みし、グラフのパスにある seqid の行をパスのトークン範囲に写す（メモリは GFF の大きさでなく、グラフにある行の数で決まる）。注釈の無いパスへは、注釈のあるパスの遺伝子をノードの共有で写す |
| 参照注釈（ann） | RepeatMasker の表とサンプルの VCF・BED を参照座標のまま持つ。閲覧器が塩基の段の列の参照位置と突き合わせる |
| リードの深さ（xdepth） | 合意座標ごとに、その座標をまたぐ整列の数をサンプルごとに数え、粗い段（1・64・4,096 座標ごとの平均）で持つ。広い範囲のリードの厚みを読み出すだけで描ける |
| タイル索引 | ノードとエッジを層ごとにタイル順（Z-order）へ並べ直したサイドカー。表示範囲の取得・件数の見積り・ハプロタイプ絞り込み・線の太さ（ハプロタイプ幅・リード支持）をすべてここから引く。矩形の問い合わせが連続した範囲の読み出しになるので、ネットワークファイルシステム上の大きな DB でも表示範囲の取得が数秒から数十ミリ秒になる。既定で作り、リードを足したときは作り直す |

いずれも DB を作り直さずに後から足せる。
