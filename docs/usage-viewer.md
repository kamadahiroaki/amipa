# アトラスを見る（`amipa serve`）

```bash
docker run --rm -p 3001:3001 -v /path/to/graph.amipa:/data:ro ghcr.io/kamadahiroaki/amipa-viewer serve
# → http://localhost:3001
```

- 開けるポートは 1 つだけ（画面も API も同じプロセスが配る）
- アトラスは読み取り専用でマウントしてよい
- 複数のアトラスを見せたいときは、それらを含む親ディレクトリを `/data` に渡す

## 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `DB_DIR` | `/data` | アトラスの置き場 |
| `PORT` | `3001` | 待ち受けポート |
| `SESSION_DIR` | — | 共有 URL 用スナップショットの保存先（唯一の書き込み先） |
| `AMIPA_READONLY` | — | `1` でノード編集の DB 保存だけを禁止。公開時は必ず付ける |
| `AMIPA_PREWARM` | 有効 | 起動時にアトラスを順読みしてページキャッシュに載せる。`off` で無効。アトラス名のカンマ区切りで対象を限定できる |
| `AMIPA_PREWARM_ON_OPEN` | 無効 | アトラスを切り替えた時にも温める |
| `AMIPA_PREWARM_MIN_MBPS` | 300 | 順読みがこの速度に届かなければ見切る |
| `AMIPA_CACHE_MB` | 64 / 512 | 接続ごとのページキャッシュ。小メモリの機械では下げる |
| `AMIPA_DB_WORKERS` | CPU 依存 | 読み取りワーカー数 |
| `AMIPA_MAX_ROWS` / `AMIPA_FETCH_MS` | — | 1 リクエストの上限（重い表示要求で全体が詰まるのを防ぐ） |

死活確認は `GET /healthz`、版の確認は `GET /api/version`。

## 主な機能

| | 内容 |
|---|---|
| 多解像度表示 | ズームに応じて表示する層が自動で切り替わる。粗い層では 1 つのノードが多数の実ノードを代表する |
| ハプロタイプ・リボン | どのサンプルやハプロタイプがどの経路を通るかを帯で表示。サンプルを選んで絞り込める |
| アノテーション | 染色体バンド・遺伝子・領域でノードを着色し、ラベルを出し、名前や座標で移動する |
| 参照座標 | `chr:位置` で移動する。ノードに参照座標を重ねて表示する |
| バブルの整列 | バブル内の各アレルを多重整列として並べ、FASTA / CLUSTAL / TSV で書き出す |
| リード整列 | 下部のパネルに塩基レベルでリードを表示する（アトラスにリードが入っている場合） |
| 図版の書き出し | 表示中の内容を SVG で保存する |
| 共有 URL | 表示位置と設定を URL に載せて共有・復元する |
| 部分の書き出し | 表示範囲の部分グラフ（GFA）とノード集合（BED） |

## 大きなアトラスを見るとき

初回の表示が遅い場合、原因はほぼディスクのランダム読みにある。

- アトラスはローカルディスクに置く。ネットワークストレージや FUSE は桁で遅くなる
- メモリを増やすと、よく見る範囲がページキャッシュに残って速くなる

## 編集を保存させたくない配信

`AMIPA_READONLY=1` で起動すると、ノード編集の DB 保存だけが塞がれる。

- 画面側は起動時に `/api/version` の `readonly` を見て、Edit 行の Save を最初から無効表示にする
  （押してから 403 で断られるのではなく、押せないことが先に分かる）
- 編集モード自体は使える。ノードを動かして繋がりを確かめる使い方はデモでもそのまま通り、
  結果が DB に残らないだけになる。動かした状態は共有 URL には載る
- サーバ側でも `POST /api/save_edits` を 403 で弾くので、画面を細工しても保存はできない
- アトラスを `:ro` でマウントしておけば二重の守りになる

大きなグラフでは編集の反映（子孫ノードと関連エッジを全層で更新する）に現実的でない時間が
かかることがある。公開インスタンスでは常に付けること。

## プリウォーム

起動直後、まだ誰も見ていない間にアトラスを順読みしてページキャッシュに載せる。既定で有効。

閲覧時のアクセスは細かいランダム読みが支配的になる。開発に使った共有ファイルシステムでは
順読みが 2.6 GB/s なのに対しランダム 4 KB は 1 回 8〜13 ms で、散ったページを 1 枚ずつ引くより
全部を順に読む方が桁で安かった（全ゲノム 230 GB を 88 秒で読み切れる）。

- 本体だけでなくサイドカー（`.reads` `.annot` `.hapidx` `.nametri`）も読む。
  本体だけ温めても、深い層の `/edges` は 18 GB のリード索引を引くので冷たいままだった（実測 100 秒）
- 4 GiB 未満のアトラスは対象外。放っておいても温まる
- 速度が出ないときは自動で見切る（`AMIPA_PREWARM_MIN_MBPS`、既定 300 MB/s）
- 進捗は `GET /api/prewarm?db=<名前>`
- `AMIPA_PREWARM_ON_OPEN=1` を既定で無効にしているのは、利用者が見たい瞬間に順読みを始めると
  最初の表示と競合してかえって遅くなるため
