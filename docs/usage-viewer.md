# アトラスを見る（`amipa serve`）

```bash
docker run --rm -p 3001:3001 -v /path/to/graph.amipa:/data:ro <registry>/amipa-viewer serve
# → http://localhost:3001
```

- 開けるポートは **1 つだけ**（画面も API も同じプロセスが配る）
- アトラスは**読み取り専用**でマウントしてよい
- 複数のアトラスを見せたいときは、それらを含む親ディレクトリを `/data` に渡す

## 設定

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `DB_DIR` | `/data` | アトラスの置き場 |
| `PORT` | `3001` | 待ち受けポート |
| `SESSION_DIR` | — | 共有 URL 用スナップショットの保存先（唯一の書き込み先） |
| `AMIPA_READONLY` | — | `1` で**編集の DB 保存だけ**を禁止。**公開時は必須** |
| `AMIPA_PREWARM` | （有効） | 起動時に DB を順読みしてページキャッシュに載せる。`off` で無効、DB 名のカンマ区切りで対象を限定 |
| `AMIPA_CACHE_MB` | 64 / 512 | 接続ごとのページキャッシュ。小メモリ機では下げる |
| `AMIPA_DB_WORKERS` | CPU 依存 | 読み取りワーカー数 |
| `AMIPA_MAX_ROWS` / `AMIPA_FETCH_MS` | — | 1 リクエストの上限（重い表示要求で全体が詰まるのを防ぐ） |
| `AMIPA_PREWARM` | — | 起動時に読み込んで温めるアトラス名。**メモリに載る見込みがあるときだけ** |

死活確認は `GET /healthz`、版の確認は `GET /api/version`。

## 主な機能

| | 内容 |
|---|---|
| **多解像度表示** | ズームに応じて表示する層が自動で切り替わる。粗い層は 1 ノードが多数の実ノードを代表する |
| **ハプロタイプ・リボン** | どのサンプル/ハプロタイプがどの経路を通るかを帯で表示。サンプルを選んで絞り込める |
| **アノテーション** | 染色体バンド・遺伝子・領域でノードを着色、ラベル表示、名前や座標で移動 |
| **参照座標** | `chr:位置` で移動。ノードに参照座標を重ねて表示 |
| **バブルの整列** | バブル内の各アレルを多重整列として表示し、FASTA/CLUSTAL/表で書き出せる |
| **リード整列** | 下部パネルに塩基レベルのリードを表示（アトラスにリードが入っている場合） |
| **図版の書き出し** | 表示中の内容をベクタ形式（SVG）で保存 |
| **共有 URL** | 表示位置と設定を URL に載せて共有・復元 |
| **部分の書き出し** | 表示範囲の部分グラフ（GFA）とノード集合（BED） |

## 大きなアトラスを見るとき

初回の表示が遅い場合、原因はほぼ**ディスクのランダム読み**。

- アトラスは**ローカルディスク**に置く（ネットワークストレージや FUSE は桁で遅くなる）
- メモリを増やすと、よく見る範囲がページキャッシュに残って速くなる
- `AMIPA_PREWARM` は**アトラス全体がメモリに載る見込みがあるときだけ**有効

## 編集を保存させたくない配信

`AMIPA_READONLY=1` で起動すると、**ノード編集の DB 保存だけ**が塞がれる。

- 画面側は起動時に `/api/version` の `readonly` を見て、**Edit 行の Save を最初から無効表示**にする
  （押してから 403 で断られるのではなく、押せないことが先に分かる）
- **編集モード自体は使える。** ノードを動かして繋がりを確かめる使い方はデモでもそのまま通り、
  結果が DB に残らないだけ。動かした状態はセッション（共有 URL）には載る
- サーバ側でも `POST /api/save_edits` を 403 で弾くので、画面を細工しても保存はできない
- アトラスを `:ro` でマウントしておけば二重の守りになる

大きなグラフでは編集の反映（子孫ノードと関連エッジの全層更新）に現実的でない時間がかかることが
あるので、**公開インスタンスでは常に付ける**。

## プリウォーム（大きいアトラスでは効く）

起動直後（まだ誰も見ていない間）に、アトラスを**順読み**してページキャッシュに載せる。**既定で有効**。

このアクセスパターンは細かいランダム読みが支配的で、共有ファイルシステムでは
**順読み 2.6 GB/s に対しランダム 4KB が 8-13 ms/回**。「散ったページを 1 枚ずつ引く」より
「全部順に読む」方が桁で安い（全ゲノム 230GB を 88 秒で読み切れる）。

- **本体だけでなくサイドカー（`.reads` `.annot` `.hapidx` `.nametri`）も読む。**
  本体だけ温めても、深層の `/edges` は 18GB のリード索引を引くので冷たいままだった（実測 100 秒）
- 4GiB 未満の DB は対象外（放っておいても温まる）
- 速度が出ないときは自動で見切る（`AMIPA_PREWARM_MIN_MBPS`、既定 300 MB/s）。
  このFSは 1 ファイルが 1 台のディスクに載るので、混んでいると桁で遅くなる
- 進捗は `GET /api/prewarm?db=<名前>`
- `AMIPA_PREWARM_ON_OPEN=1` で「DB を切り替えた時」にも温める（既定 OFF。
  利用者が見たい瞬間に順読みを始めると最初の表示が競合して逆に遅くなるため）
