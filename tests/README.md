# 回帰試験

「前は通っていたものが、直したせいで壊れていないか」を同じ手順で確かめる。
**上から順に重くなる。** 直した範囲に応じて必要な段まで走らせる。

| 段 | 守るもの | 要るもの | 所要 |
|---|---|---|---|
| `format` | 容器・索引・cs 切り出しが仕様どおりか（単体） | python3 + zstandard | 数秒 |
| `image` | 焼いたイメージで povu が起動し、依存と共有ライブラリが揃うか | — | ビルド時に自動 |
| `e2e` | GFA → アトラス → `amipa check` が全部 ok になるか。段の連結と再開の判定 | 小さい GFA（chrY） | 2〜4 分 |
| `api` | 生きた backend が**空でない**応答を返すか（35 項目） | 起動中の viewer とアトラス | 分 |

```bash
tests/run.sh format
tests/run.sh e2e  --gfa /path/chrY.gfa
tests/run.sh api  chrY.layered.db localhost:3001
```

`image` の段は独立した script ではない。`docker/Dockerfile.*` と `docker/amipa-*.def` の
最終段に自己テストが入っていて、**共有ライブラリの取りこぼしはビルドの時点で落ちる**。

## 何を「失敗」とみなすか

`api` の判定（`judge.py`）は **200 が返っただけでは通さない**。`error` キー付きの 200 と、
**空配列**の両方を失敗にする。矩形の取り違えで `[]` が返り「速い！」と誤読した事故が
実際にあったため。データが無いのが正常な機能にだけ `allow-empty` を付ける。

同じ理由で、リクエストに使う座標・層・ノード名・hap 範囲は**決め打ちしない**。
`pick.py` が **DB 自身の応答から取る**（グラフが変わっても的を外さない）。

## 追加するときの置き場

- 外部データが要らないもの → `format/`（速いので毎回走らせる）
- アトラスを作る必要があるもの → `e2e/`
- 起動中の backend に問い合わせるもの → `api/`（`verify_api.sh` に 1 行足す）

★HPC 固有の投入手順（qsub の書式・ノードの都合）はここに書かない。
それは `amipa-lab/hpc/` の側の話で、ここは**どの環境でも同じように走る**ものだけを置く。
